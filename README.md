# nba-game-prediction

A work-in-progress NBA data project with three parts:

1. A small ingestion pipeline. A Prefect flow pulls the live NBA scoreboard and lands the raw JSON in S3, a script loads the newest file into Snowflake, and a second Prefect flow runs dbt.
2. Two notebooks that train baseline win/loss classifiers on historical game data.
3. A React app that lists upcoming games with the bookmaker-implied favourite for each.

The parts are not wired together yet. The pipeline loads raw scoreboard JSON but has no NBA-specific dbt models, the notebooks read their own data, and the web app gets its numbers from a betting-odds API rather than from the notebook models. See [Known gaps](#known-gaps).

Web app demo: https://nba-predictions-app.vercel.app

## Repository layout

| Path | What it is |
| --- | --- |
| `data_ingestion/fetch_nba_data.py` | Prefect flow. Fetches today's live scoreboard with `nba_api`, logs it at INFO level, and writes it to `s3://$S3_BUCKET_NAME/raw/nba_scoreboard_<YYYYMMDD_HHMMSS>.json`. The fetch and upload tasks retry three times, five minutes apart. |
| `data_ingestion/move_nba_data_to_sf.py` | Plain Python script. Creates the table `RAW_NBA_SCOREBOARD (game_data VARIANT)` if it does not exist, finds the most recently modified object under `raw/` in the bucket, creates or replaces an external stage `nba_stage` on `s3://$S3_BUCKET_NAME/raw/` with the AWS key pair from `.env`, and runs `COPY INTO` for that one file. The stage statement is logged with the key pair masked. |
| `data_transformation/transform_data.py` | Prefect flow that shells out to `dbt run --select my_first_dbt_model --project-dir $DBT_PROJECT_DIR`, logs dbt's output (at INFO level when dbt succeeds, at ERROR level when it fails), and exits with status 1 if dbt fails. |
| `nba_dbt/` | dbt project created with `dbt init`. It still contains only dbt's starter example models. |
| `notebooks/predict_past.ipynb` | Season-by-season backtest of a ridge classifier on historical team box scores. |
| `notebooks/predict_live.ipynb` | Exploratory notebook: random forest on game logs pulled from `nba_api`, then predictions for today's and tomorrow's schedule. |
| `nba-predictions-app/` | React 19 + Vite + Tailwind CSS frontend, with its own [README](nba-predictions-app/README.md). |
| `requirements.txt` | The Python packages the scripts and notebooks import, plus `dbt-core` for the `dbt` command. |
| `prefect.yaml` | Generated by `prefect init` (Prefect 3.1.5). No deployments are defined yet; the flows are run directly. |

## Pipeline

```
NBA live scoreboard (nba_api)
        |   data_ingestion/fetch_nba_data.py        (Prefect flow)
        v
S3      s3://<bucket>/raw/nba_scoreboard_<timestamp>.json
        |   data_ingestion/move_nba_data_to_sf.py   (stage + COPY INTO)
        v
Snowflake   RAW_NBA_SCOREBOARD (one VARIANT column)
        |   data_transformation/transform_data.py   (Prefect flow -> dbt run)
        v
dbt     nba_dbt/  (starter models only)
```

All three scripts read their settings from a `.env` file in the repository root (it is git-ignored).

## Notebooks

### `predict_past.ipynb`

Predicts whether a team wins its next game from box-score statistics.

- Input: `nba_games.csv` in the repository root. The file is not included in the repo (it is git-ignored). In the saved run it has 17,772 team-game rows and 150 columns covering 27 October 2015 to 16 June 2022. Those figures are the same as in Dataquest's own notebook (see below), whose README links the CSV it uses: team box scores scraped from Basketball Reference.
- Target: the `won` value of the same team's next game.
- Model: `RidgeClassifier` on min-max scaled features, with 30 features chosen by forward `SequentialFeatureSelector` using a three-fold `TimeSeriesSplit`.
- Evaluation: a backtest that, for each season from the third one onward, trains on all earlier seasons and predicts that season.

Results stored in the notebook output:

| Features | Backtest accuracy |
| --- | --- |
| Previous game's box score only | 54.9% |
| Plus 10-game rolling averages for the team and its next opponent, and the next game's home/away flag | 63.2% |

For reference, the home team wins 57.2% of the games in the same data, so the first model is worse than always picking the home team and the second is about six points better. The scaler and the feature selector are both fit on the whole dataset before the backtest runs, so the seasons used for testing also influence which features are chosen. Read the accuracy figures with that in mind.

This notebook follows Dataquest's NBA game prediction project walkthrough, [`nba_games/predict.ipynb` in dataquestio/project-walkthroughs](https://github.com/dataquestio/project-walkthroughs/tree/master/nba_games). The helper functions (`add_target`, `backtest`, `find_team_averages`, `shift_col`, `add_col`), the model settings and the backtest are the walkthrough's. The main changes here are explanatory markdown cells, a few extra print cells, a `find_team_averages` that drops non-numeric columns before taking the rolling mean, and two closing cells that fetch the live scoreboard with `nba_api` without predicting anything from it.

### `predict_live.ipynb`

Pulls every team's game log with `nba_api`'s `LeagueGameFinder`, trains a `RandomForestClassifier` on five features (team, opponent, the team's average points per game, a home/away flag and a last-game-result flag), and then scores the games returned by `ScoreboardV2` for today and tomorrow. The saved run reports 58.9% accuracy on a random 80/20 split. Treat that number as indicative only: the split is not time-ordered, and the points-per-game feature is an average over each team's whole history. The final cell that scores upcoming games looks team statistics up by raw NBA team id after that column has been label-encoded, so it falls back to default values; its printed probabilities are not meaningful forecasts.

## Web app (`nba-predictions-app/`)

The app calls The Odds API (`api.the-odds-api.com/v4/sports/basketball_nba/odds`, US region, head-to-head market, decimal odds). For each game it takes the first bookmaker's prices, converts them to implied probabilities, normalises the two so they sum to 100% (removing the bookmaker's margin), and shows the more likely side as the "prediction" with that probability as the "confidence". It does not use the models from the notebooks, and the page says so.

Other behaviour, as implemented in `src/`:

- Game cards are sorted by confidence, then by start time. Odds are displayed in American format. Team logos load from `cdn.nba.com`, with a coloured-initials placeholder if an image fails.
- In a production build the app calls the API directly first and, if that fails, tries a list of public CORS proxies; in development it goes straight to the proxies.
- A failed load is retried three times, two seconds apart. If every attempt fails the page ends on an error panel with Try Again and Reload Page buttons. The code also contains an automatic switch to eight hard-coded sample games, but it does not stay on screen (see the app README). The sample games are shown when the button that switches between live and sample data is used.
- Data is refreshed every 15 minutes. `Ctrl+Shift+D` toggles a small debug panel.

Details are in [`nba-predictions-app/README.md`](nba-predictions-app/README.md).

## Running it

### Pipeline

Requires Python 3, an AWS account with an S3 bucket, and a Snowflake account. The project was developed in a Python 3.9 virtualenv. `requirements.txt` does not pin versions, apart from capping pandas below 3 for the notebooks. A clean install of it was last checked on Python 3.13 in October 2026.

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Create `.env` in the repository root:

```
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_REGION=us-east-1
S3_BUCKET_NAME=...

SNOWFLAKE_USER=...
SNOWFLAKE_PASSWORD=...
SNOWFLAKE_ACCOUNT=...
SNOWFLAKE_ROLE=...
SNOWFLAKE_WAREHOUSE=...
SNOWFLAKE_DATABASE=...
SNOWFLAKE_SCHEMA=...

DBT_PROJECT_DIR=/absolute/path/to/nba-game-prediction/nba_dbt
```

`AWS_REGION` is optional and defaults to `us-east-1`. Then run the steps in order:

```bash
python data_ingestion/fetch_nba_data.py
python data_ingestion/move_nba_data_to_sf.py
python data_transformation/transform_data.py
```

With no Prefect API configured, Prefect 3 starts a temporary local server for the duration of each flow run.

The two flows write most of their own messages at INFO level through Python's `logging` module: the scoreboard JSON in the ingestion flow, and the dbt command and its output when dbt succeeds. Importing Prefect puts its own handler on the root logger at WARNING level, which turns the scripts' later `logging.basicConfig(level=logging.INFO, ...)` call into a no-op. By default, then, those lines are not printed; only Prefect's own lines and the scripts' ERROR lines are. Set `PREFECT_LOGGING_ROOT_LEVEL=INFO` to see them (other libraries' INFO lines are printed too). This was checked with Prefect 3.8.8. `move_nba_data_to_sf.py` does not import Prefect, so its INFO lines are always printed.

The dbt step additionally needs things that are not in this repository: a dbt adapter for your warehouse (`requirements.txt` lists only `dbt-core`; for Snowflake that means `pip install dbt-snowflake`) and a profile named `nba_dbt` in `~/.dbt/profiles.yml`.

### Notebooks

`requirements.txt` covers what the notebooks import (`pandas`, `numpy`, `scikit-learn`, `matplotlib`, `seaborn`, `shap` and `nba_api`). Jupyter itself is not listed; install it separately, for example with `pip install notebook`.

pandas is capped below 3 because `predict_past.ipynb` relies on pandas 2 behaviour: on pandas 3 its first `groupby(...).apply(...)` drops the `team` column and the next cell fails.

`predict_past.ipynb` needs `nba_games.csv` in the repository root; `predict_live.ipynb` downloads its data from the NBA stats API when it runs.

### Web app

Requires Node.js 18, 20, or 22 and later (the range Vite 6 accepts) and an API key for The Odds API.

```bash
cd nba-predictions-app
npm ci
echo "VITE_SPORTS_API_KEY=<your Odds API key>" > .env
npm run dev
```

`VITE_ODDS_API_KEY` is accepted as an alternative variable name. The API module throws on load if neither is set, so a key is needed even to see the sample data. Other scripts in `package.json`: `npm run build`, `npm run preview`, `npm run lint`.

## Known gaps

- **No real dbt models.** `nba_dbt/` has only the `dbt init` examples, so the raw scoreboard JSON in Snowflake is not yet flattened into game or team tables, and nothing downstream reads from the warehouse.
- **Models and app are separate.** The web app's "prediction" is the bookmaker favourite. Serving the notebook model's output to the app has not been built.
- **No orchestration beyond single flows.** There is no schedule, no Prefect deployment, and the S3-to-Snowflake step is a script rather than a flow.
- **The already-loaded check is not expected to work.** Before copying, `move_nba_data_to_sf.py` runs `SHOW COPY HISTORY ON TABLE RAW_NBA_SCOREBOARD LIMIT 100` to see whether the file was loaded before. Snowflake's SQL reference lists no such `SHOW` command (load history is exposed through the `COPY_HISTORY` table function), and the function's own docstring anticipates a syntax error. When the statement fails, the script logs the error and runs `COPY INTO` anyway. This has not been re-run against Snowflake.
- **The S3 listing is not paginated.** `move_nba_data_to_sf.py` makes a single `list_objects_v2` call, which returns at most 1,000 keys, so with more files than that under `raw/` it would stop seeing the newest one.
- **The Odds API key is exposed to the browser.** Vite inlines `VITE_*` variables into the client bundle, and the proxy fallback sends the full request URL, key included, to third-party CORS proxies. This is acceptable for a throwaway free-tier key only. `nba-predictions-app/API_TROUBLESHOOTING.md` sketches the server-side proxy that would fix it.
- **No tests** for the Python code or the frontend. The frontend has no type-check step, and its ESLint configuration only covers `.js` and `.jsx` files, not the TypeScript sources.
